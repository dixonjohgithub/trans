GitHub Copilot — best practices

GitHub Copilot  native to VS Code; leanest on the everyday, high-frequency work
Memory — user rootSet personal custom instructions in VS Code settings for individual style preferences (naming, comment style, preferred libraries). These take highest priority and stay with the developer, not the repo.
Memory — project rootCommit .github/copilot-instructions.md at the repo root for team-wide conventions (architecture, testing, do/don't). AGENTS.md is also recognized. Keep it short and factual — only what's true for the whole repo.
Memory — folder / pathAdd path-specific files under .github/instructions/*.instructions.md with an applyTo glob (e.g. applyTo: "src/api/**"). Prefer several narrow files over one giant instruction file so rules only load where relevant.
Plan modeUse the built-in Plan chat mode (or a custom read-only *.chatmode.md) to produce an implementation plan before letting agent mode edit. For background work, the cloud coding agent posts its plan on the pull request for review before it proceeds.
Scoping context (token saving)Reference context precisely with #file and #selection rather than broad @workspace, which pulls in far more. Use prompt files (*.prompt.md) for repeatable, pre-scoped tasks. Use organization content exclusion to keep sensitive or irrelevant files out of context entirely.
SubagentsNo first-class subagent system like Claude. Delegation is handled by the cloud coding agent and by custom agents / custom chat modes; use prompt files as lightweight, reusable "specialist" configurations.
Parallel agentsAssign multiple GitHub issues to the cloud coding agent to run in parallel, each in its own isolated Actions environment. In-editor agent mode is a single interactive session — parallelism comes from the cloud agent, not the IDE.
MCP integrationsConfigure MCP servers for agent mode in .vscode/mcp.json (workspace) or, for the cloud agent, in repository settings. Enable only the servers a task needs — each server's tools add to context.
Secrets managementReference secrets as ${input:my_secret} in mcp.json: Copilot prompts once, stores securely, and never writes the value to disk. For the cloud agent use dedicated Agents secrets/variables (org- or repo-level); prefix MCP secrets with COPILOT_MCP_. Enable secret scanning via the GitHub MCP server to catch leaked credentials before commit.
Other tool-specificLean on prompt files and custom chat modes to standardize team workflows; use Copilot code review with custom instructions for consistent PR feedback; pick the right model per task from the model picker; enforce org-level policies and content exclusion centrally.

Claude — best practices

Claude  used via VS Code extension + command line; strongest at wide-context reasoning
Memory — user rootPut personal, cross-project defaults in ~/.claude/CLAUDE.md (your workflow, preferred commands, global conventions). Applies to every project; keep it short so it doesn't crowd out project context.
Memory — project rootCommit ./CLAUDE.md at the repo root for team-shared architecture, conventions, and build/test commands. Discipline: write only what's true every session, keep it under ~150–200 lines, and point to detail rather than pasting it. Personal, uncommitted overrides go in CLAUDE.local.md (gitignored).
Memory — folder / subdirPlace a CLAUDE.md in a subdirectory (e.g. frontend/CLAUDE.md) for module-specific rules. It loads lazily — only when Claude reads a file in that folder — so a large monorepo doesn't bloat context. Compose files with @path imports.
Plan modeEnter plan mode (Shift+Tab to cycle) for large or ambiguous tasks — Claude investigates read-only and proposes a plan without editing. Invest effort in the plan so the implementation can be "one-shot," and review it before approving execution.
Scoping context (token saving)Run /clear between unrelated tasks and /compact to summarize long sessions. Name specific files instead of letting Claude read broadly. Keep memory files lean. Offload research to subagents so the main session's context stays small, and route simpler work to a lighter model.
SubagentsDefine specialists in .claude/agents/*.md (YAML frontmatter: name, description, tools, model, mcpServers, isolation). Each runs in its own isolated context and returns only a summary — ideal for research, verification, and code review without polluting the main window.
Parallel agentsLaunch multiple subagents at once; add isolation: worktree so each works in its own git worktree without collisions. Parallel agents share the prompt cache, so fanning out (tests, docs, refactor, audit at once) is efficient. Note: worktrees/subdirs of one repo share a single auto-memory directory.
MCP integrationsAdd servers at user, project, or local scope; commit project servers in .mcp.json so the team shares them. Grant individual subagents only the mcpServers they need, and keep the active set minimal to limit tool-definition tokens.
Secrets managementNever put secrets in CLAUDE.md — it's committed. Use environment variables / .env (gitignored) and pass credentials to MCP servers via env, not prompts. Lock down what Claude can run with /permissions allowlists and hooks, and manage allow/deny rules in settings.json.
Other tool-specificAdd reusable slash commands in .claude/commands/; use hooks for deterministic gates (auto-format, run tests) so the model doesn't have to; run /review for structured code review; and route models deliberately — a lighter model for routine work, the strongest only when the task demands it.

Devin.AI — best practices

Devin.AI  runs on its own platform; best for long, hands-off, and parallel work
Memory — org / user rootUse Knowledge for general facts Devin should reference in every session — style guides, architecture, org conventions. Add it once so Devin stops asking or re-deriving the same context.
Memory — project / repoScope Knowledge to the relevant repo, and invest in repo setup once: install dependencies, define test/lint/build commands, env, VPN, and DB. Machine snapshots let every future session start ready to go.
Memory — task / "folder" levelCreate Playbooks for recurring tasks — a Playbook is like a custom system prompt for a repeated job (e.g. "add an endpoint," "cut a release"). Reach for one whenever you notice yourself repeating the same instructions.
Plan modeDevin drafts a plan for each task before it starts working. Review and edit that plan — especially for ambiguous work — before letting it proceed. Clear, complete specs up front dramatically reduce mid-task re-planning.
Scoping context (token saving)Write tightly-scoped tickets with clear acceptance criteria and the relevant file paths. Lean on Knowledge and Playbooks so Devin doesn't re-read or re-learn context each run. Smaller, well-defined tasks finish with less work.
SubagentsUse managed Devins: a lead session delegates sub-tasks to child Devins, each a full Devin with its own VM. The lead scopes the work, monitors progress, resolves conflicts, and compiles the results.
Parallel agentsRun multiple sessions or managed Devins in parallel, each in an isolated VM — ideal for fanning out across independent tickets. Keep each task self-contained so parallel runs don't conflict.
MCP integrationsConnect Devin to external tools through its large MCP connector catalog plus 20+ native integrations (issue trackers, chat, source control, cloud & data services). Enable only what a workflow needs.
Secrets managementStore credentials in Devin's Secrets / environment-variable manager in the dashboard — never paste API keys into the chat prompt. Secrets are scoped (personal or org) and auto-retrieved in future sessions; consider direnv in repo setup for env vars.
Other tool-specificFront-load environment setup (snapshots, test commands) so sessions start productive; always review Devin's pull requests before merge; write clear tickets to minimize clarification loops; and manage/monitor from the VS Code extension while the work runs on Devin's platform.
Practitioner reference for tool configuration and workflow discipline. Product mechanisms (file names, flags, settings) change frequently — reconfirm against current official documentation before standardizing across teams. Sources: Claude Code, GitHub Copilot, and Devin documentation (2026).
